# DEC-018 — Restore no-outreach and authorize bounded public Bambu Connect / Network Plugin feasibility evaluation

- **Date:** 2026-09-06
- **Status:** Approved / current M2 viability decision
- **Decision:** Restore and preserve the Product Owner's DEC-011 no-outreach constraint. The project will not contact Bambu Lab or pursue developer-partner authorization. DEC-017 is superseded to the extent that it made vendor outreach/partner authorization the continuation gate. The project may perform one bounded M2 feasibility evaluation using only publicly documented/supported Bambu Connect and updated Network Plugin boundaries. Bambu Connect may be used only as a documented user-mediated authorization/action handoff. A user-installed official Bambu Network Plugin may be evaluated for printer discovery, local connection and read-only monitoring through public integration declarations/behavior. The project must not redistribute or copy the proprietary plugin, reverse engineer its binary/security mechanisms, impersonate Bambu cloud clients, extract Bambu Connect/Studio tokens or credentials, use undocumented/private Bambu Cloud APIs, enable Developer Mode, weaken security controls, or execute printer write/control operations in M2.
- **Rationale:** The Product Owner explicitly rejected Bambu outreach and reaffirmed that this had already been a no-go. Bambu's public documentation nevertheless provides a no-contact interoperability route: Bambu Connect is documented for restricted third-party handoffs, while Bambu states unofficial software can explore the updated Network Plugin for monitoring. Bambu Studio public source exposes an integration boundary with discovery/local-message callbacks without granting redistribution rights to the separately distributed proprietary plugin. This warrants one final constrained feasibility spike before terminating the project.
- **Alternatives considered:** Vendor/developer-partner outreach — rejected by Product Owner. Reverse-engineered Bambu Cloud access/client impersonation — rejected by vendor boundary and DEC-006. Further custom mDNS/SSDP experimentation — rejected after repeated hands-on failure. Immediate project termination — deferred until this final public supported integration surface is tested.
- **Consequences:** `prompts/codex/NEXT_PROMPT.md` may be QUEUED for a feasibility spike only. The plugin, if needed, must be user-installed through an official Bambu distribution path; the repository must not bundle/download/redistribute it. Any bridge must be independently implemented and narrowly read-only. Permanent adoption of a proprietary runtime dependency still requires a separate Product Owner architecture/dependency/licensing decision after successful feasibility evidence. If the spike cannot reliably discover/connect/monitor the Product Owner's A1 Mini and X2D without prohibited techniques, recommend M2 NO-GO and project termination. M3 remains blocked and PR #3 remains draft/unmerged.
